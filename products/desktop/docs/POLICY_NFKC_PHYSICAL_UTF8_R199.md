## Specific reproducible defect

R198 guarded NFKC direct-API hunk source rows using len(source) as its purported 10 MiB *UTF-8 byte* budget. Unicode code points occupy one Python character but can consume 2–4 UTF-8 bytes. A single source row of over 10 MiB UTF-8 could pass that count. The guard also accepted fabricated "physical line" rows containing embedded newline characters, Unicode line separators or unpaired surrogates. Those inputs are not generated by the bounded actual TXT/MD/CSV reader but could be supplied by direct callers or future integration changes. This is local API integrity hardening, not evidence of a remote GUI exploit.

## Implemented

- Count encoded strict UTF-8 bytes per before/after side across all hunks, not Python characters. Reject if either side exceeds 10 MiB.
- Reject unpaired surrogate strings that cannot be encoded by the reader's UTF-8 decoder.
- Require each source text to be exactly one nonempty splitlines(keepends=True) item; valid LF, CRLF, CR, unterminated-final and blank-newline rows still pass.
- Validate all input before returning any review cues; retain R198 exact native keys, containers, source coordinates and 50,000-line constraint. Skip long valid rows for cue rendering only. Do not mutate input, original bytes or source SHA-256.
- No legal/compliance equivalence, payment approval, cloud uploads, telemetry or financial Decimal pathways changed.
