## Why this new lane matters (not another substitute email)
Past Dispatch QA provides static HTML previews and a few newsletter-transport guards, but it does **not** inspect the *actual MIME body* of an authorized received Jetpack message. It cannot yet prove that legal and affiliate disclosures survived WordPress rendering, that an unsubscribe footer is clickable, or that the native From/Subject/preheader are faithful to the draft. The new **offline** `received_eml_preflight.py` examines a local .eml file only after one already exists through a separately authorized delivery. This script is never a sender, signup tool, address scraper or list manager. A synthetic fixture is deliberately rejected as recipient evidence.

Public /dispatch/ and /focus/ are published; Focus URL/CSS-based false-success signal remains under Claude/Site QA review (#1272 and competing #1276), not live-fixed by this package.

**No test mail authorized.** WordPress documents `Preview email` as a non-sending editor preview, but `Send test email` actually emails a recipient. Neither a static HTML file nor a `Preview email` screenshot is a genuine received MIME message. WordPress's real editor preview is still required to verify desktop/mobile rendering; a received-message evidence check remains a separate gate after founder explicitly authorizes delivery. The source tool cannot change those restrictions.

## Safe manual usage — only if an actual authorized received .eml is later available
1. Use a locally saved, legitimately authorized received message. Keep it **out of GitHub**; private subscriber addresses, body, Message-ID and metadata remain private. Never use unrelated inbound messages as a substitute for the Jetpack campaign.
2. Copy `evidence-attestations.template.json` privately and record only verified booleans from source-of-truth records. Do not set flags based on this test file, Jetpack counts or a fictitious account. Do not record postal addresses or recipient addresses in GitHub.
3. Run locally: `python -I received_eml_preflight.py --eml /private/authorized-received.eml --kind editorial --attestations /private/evidence.json --output /private/redacted-report.json`. For Issues 03/05 use `--kind commercial` **only after** named merchant permission and offer-specific links are independently authenticated.
4. Review the aggregate redacted JSON with independent QA. It contains booleans and gate names only, not sender/recipient addresses, actual subject text or HTML.
5. Perform **separate** human visual review of native email desktop/mobile, actual unsubscribe click behavior (only on a specifically approved QA account), publisher-controlled physical mailing-address validity and real Fieldbook receipt. The script cannot prove these. No sending/publishing or list change follows from a PASS.

## Fail-closed checks and limitations
- Checks From presence and recognizable Final Vestige display, nonempty Subject, MIME HTML and plaintext, visible first-party CTA, no `[INSERT...]` or `{{...}}` placeholders.
- Checks unsubscribe wording and an HTTPS clickable text link in HTML; separately reports the List-Unsubscribe and optional RFC 8058 one-click headers. **Presence does not prove real opt-out functionality**, which requires a separately authorized browser test.
- Checks a near-message merchant disclosure for commercial drafts; seller research citations are not affiliate approval. Flags common affiliate earning-link hosts as unactivated for this *preclearance* mode. When authenticated approval arrives, the scanner needs a separately reviewed exact allowlist / partner terms integration; do not silently drop the control.
- Human attestations: actual authorized received mail (and *not* synthetic), valid **Final Vestige** postal address visibly included (Automattic's address does **not** qualify), real opt-out completed, provider-native recipient eligibility, actual welcome/Fieldbook receipt, explicit founder final campaign release approval; commercial issues also require **named** affiliate approval, EMAIL rights and authorized earning-link format.
- Tool always emits `HOLD_UNSENT`, including if all fixture booleans are set true. It is a **read-only evidence aid**, not legal certification or release authority. A header alone never proves delivery, SPF/DKIM, compliant address or lawful treatment. Missing body formats are held conservatively; this is a production QA policy, not a statutory requirement for multipart/alternative.
- No A/B statistics with ~3 reported accounts. No fabricated signups, emails delivered, affiliate commissions or settled purchases.
